# Chapter 3 讲义：Collecting data

## 这份讲义怎么用

- 这是一份给“第一遍阅读”准备的讲义版，不要求你先读原文。
- 目标不是覆盖原书每个代码片段，而是先帮你抓住这一章真正重要的主线。
- 第二遍再回原文时，你只需要带着这份讲义去对照图表、代码和作者的细节展开。

## 本章在全书里的位置

Chapter 1 帮你建立了“投资世界地图”，Chapter 2 帮你补了“财务语言”和“指标语境”，Chapter 3 则是在回答：

“我现在知道该看什么了，那这些数据到底从哪里来、怎么拿、怎么放进自己的研究流程里？”

所以这章是从“概念理解”切到“研究输入层”的一章。

## 这一遍你最需要获得什么

读完这份讲义后，你至少应该得到 5 个稳定结论：

1. 金融数据至少分成三类：`fundamental`、`technical`、`nonfinancial`
2. 平台、API、notebook、scraping 不是同一层东西，不能混着理解
3. 个人研究的早期阶段，优先 notebook，不要一上来就产品化
4. `yfinance` 是一个很适合起步的工具，但不是无条件可靠的长期底座
5. 数据源的稳定性、覆盖范围和替换成本，会直接影响你的研究系统设计

## 一页主线

如果把这一章压成最短的一条线，它其实是在讲：

1. 先搞清楚你要的是什么数据
2. 再选合适的入口去拿数据
3. 先在 notebook 里探索，而不是先做成 app
4. 先用 `yfinance` 跑通最小流程
5. 同时保留“以后换数据源”的架构意识

你可以把这一章理解成：

“投资研究系统的数据接入层入门”

## 核心概念讲解

### 1. 金融数据不是一种数据

这一章最先要求你分清三种数据：

| 数据类型 | 它在看什么 | 典型内容 | 你应该怎么理解 |
| --- | --- | --- | --- |
| 基本面数据（fundamental data） | 公司底子怎么样 | 三张表、比率、公司披露 | 更像在看企业运行状态 |
| 技术数据（technical data） | 市场过去怎么给它定价 | 价格、成交量、收益率、波动 | 更像在看市场行为和时间序列 |
| 非财务数据（nonfinancial data） | 数字之外发生了什么 | 新闻、情绪、舆情、文本 | 更像在补语境和解释层 |

这里最容易犯的错是：

- 还没分清自己要哪类数据，就直接找库
- 以为所有“金融数据”都可以用同一套方法理解

这一章要你先建立一个习惯：

“先问我现在缺的是哪一类数据，再问我要用哪个工具。”

### 2. 平台、API、scraping、notebook 到底是什么关系

这是本章最值得一次性理顺的一组概念。

| 概念 | 它是干什么的 | 更适合谁 | 主要问题 |
| --- | --- | --- | --- |
| 平台（platform） | 给人看数据、做筛选、看图表 | 人类用户 | 适合浏览，不一定适合程序稳定接入 |
| API | 给程序取数据的正式接口 | 程序和脚本 | 需要理解权限、格式、调用限制 |
| scraping | 直接从网页表面扒数据 | 临时性脚本 | 脆弱、易失效、容易被反爬 |
| notebook | 交互式分析环境 | 做研究的人 | 不是数据源，而是工作环境 |

你可以把它们想成：

- 平台：前台页面
- API：后端接口
- scraping：绕开正式接口、直接拆前台页面
- notebook：你自己的实验台

这里你要额外记住一点：

很多网站会主动做反爬，所以 `scraping` 的真正风险不是“今天抓不到”，而是“未来不稳定”。网站只要改页面结构、加验证码、限频、封 IP，或者把某些数据改成更难解析的方式，原来的抓取代码就可能立刻报废。

所以在工程上更稳的判断是：

- `scraping` 可以作为入门、过渡或补洞方案
- 但正式 `API` 才更适合做长期研究系统的稳定输入

### 3. 为什么作者强调 notebook

很多程序员一看到“我能拿数据了”，就会自然想做：

- 小网站
- 可视化 dashboard
- 自动化前端工具

但作者在这一章明确站在“研究效率”的角度提醒你：

研究早期更重要的是：

- 快速试错
- 快速看中间结果
- 快速改筛选条件
- 快速画图和验证想法

这正是 `Jupyter`、`Databricks` 这类 notebook 擅长的场景。

所以这里的真正结论不是“应用不重要”，而是：

“在研究问题还没稳定之前，别把主要精力花在壳子上。”

### 4. `yfinance` 是什么，它为什么重要

`yfinance` 是一个 Python 库，常被用来获取 Yahoo Finance 相关来源中的金融数据。

这本书为什么用它起步，不是因为它最权威，而是因为它有这几个优点：

| 维度 | 为什么它适合入门 |
| --- | --- |
| 上手门槛 | 低，几行代码就能开始 |
| 数据种类 | 能拿价格、部分公司信息、财务报表、部分指标 |
| 社区资料 | 很多示例和教程可参考 |
| 学习价值 | 能快速把 Chapter 2 里的术语变成 DataFrame 和时间序列 |

你现在不用把它想得太复杂。第一遍只要记住：

- 你给它一个 `ticker`
- 它能返回某家公司或某个资产的一些数据对象
- 这些对象可以继续变成表格、时间序列和分析输入

比如在概念上，它能帮你做三类事：

| 任务 | 例子 |
| --- | --- |
| 抓基本面 | 利润表、资产负债表、现金流量表 |
| 抓技术数据 | 历史价格、收益率、波动 |
| 抓辅助信息 | 部分公司资料、部分指标、分红拆股信息 |

### 5. `yfinance` 为什么又不是“最终答案”

这一章不是在神化 `yfinance`，反而很认真地给它划边界。

书里的关键提醒是：

- `yfinance` 依赖 Yahoo 的接口和网页结构
- 它本身不是 Yahoo 官方维护的正式商业产品
- 如果上游改动、字段变化、反爬策略收紧，你的脚本可能失效

所以作者真正想教你的，是这一句：

“先用 `yfinance` 跑通最小可用流程，但不要把它误当成永久可靠底座。”

这也是程序员最该熟悉的一种工程判断：

- 原型能用
- 不等于生产可依赖

### 6. 商业数据源为什么要提前知道

后半章提到 `Finviz`、`EODHD`、`Alpha Vantage`、`OpenBB`，不是要你马上都学会，而是要你建立“替代方案意识”。

你只需要先知道这几件事：

| 名称 | 第一眼该怎么记 |
| --- | --- |
| `Finviz` | 美股筛选器很强，但覆盖面偏美国市场 |
| `EODHD` | 更像专门卖数据的服务，国际市场覆盖更广 |
| `Alpha Vantage` | 也是 API 数据服务，免费版可用但有限制 |
| `OpenBB` | 不只做股票，更适合多资产研究 |

这一段真正想留下来的不是“产品清单”，而是：

- 数据源有覆盖范围差异
- 免费版和付费版有边界
- 接口风格接近时，迁移成本更低
- 提前知道替代方案，后面系统才不容易被单点锁死

## 本章最值得抓住的 4 个判断

### 判断 1：先分数据类型，再谈工具

如果你反过来做，很容易出现这种情况：

- 拿到了很多数据
- 但不知道这些数据本来是为了解答什么问题

### 判断 2：平台适合看，API 适合接，scraping 适合救急

这几者没有谁“绝对更高级”，但它们的适用场景不同。

作者明显更鼓励你：

- 优先用正式接口
- 把 scraping 留给过渡期或特殊场景

### 判断 3：第一阶段先做研究，不先做产品

如果还没跑通研究流程就先做应用，你很容易把时间消耗在：

- 界面
- 部署
- 交互
- 维护

而不是消耗在真正重要的：

- 数据
- 假设
- 比较
- 结论

### 判断 4：工具只是入口，系统设计才是长期重点

本章虽然表面在讲库，但底层在讲的其实是：

- 数据源怎么选
- 数据结构怎么统一
- 后面怎么替换
- 哪些地方会成为脆弱点

这已经很接近程序员做系统设计时的思路了。

## 第一遍不用深究的内容

为了防止第一遍就陷进细节里，你现在可以主动放过这些东西：

- 每个库的安装细节
- 每段代码的参数细节
- 统计公式的严格数学推导
- 商业数据源的定价细节
- 每个平台全部功能差异

第一遍你真正要抓的是：

- 数据分类
- 接入边界
- 工具定位
- `yfinance` 的价值与限制
- 替代方案意识

如果这份讲义读完了，理想状态下你应该能用自己的话说出下面这些句子：

3. “`yfinance` 很适合我先把流程跑通，但我不能默认它永远稳定。”
4. “商业数据源不是为了显得高级，而是为了更稳定、更广覆盖或者更明确的服务边界。”
5. “这章真正教我的不是某个库，而是数据工作流的思路。”
