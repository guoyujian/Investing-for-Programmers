# Chapter 6 讲义：Building an asset monitor

## 这份讲义怎么用

- 这是一份给“第一遍阅读”准备的讲义版，不要求你先读原文。
- 目标不是覆盖第六章所有 notebook 代码，而是先帮你抓住这章的系统设计主线、代表性例子和最关键的数据整合思路。
- 第二遍回原文时，你只需要带着这份讲义去对照架构图、表格模板和各资产处理逻辑。

## 本章在全书里的位置

如果说：

- Chapter 3 教你怎么拿数据
- Chapter 4 教你怎么研究成长 thesis
- Chapter 5 教你怎么理解收入型资产

那么 Chapter 6 就是在问：

“这些东西怎么真正收进一个我能长期维护的个人系统？”

所以这一章非常关键。它是全书里最像“从学习投资，走向搭自己的投资操作系统”的章节之一。

## 这一遍你最需要获得什么

读完这份讲义后，你至少应该拿到 5 个稳定结论：

1. `asset monitor` 不是记账表，而是持仓控制面板
2. 真正困难的地方不在算收益，而在多源数据整合
3. 统一 schema、ticker 映射、货币转换是实务里的硬问题
4. stocks、ETFs、bonds、crypto 可以放进一个系统，但不能按同一逻辑处理
5. 这一章是在把前面几章的能力沉淀成一个长期工具

## 一页主线

如果把这一章压成最短的一条线，它其实是在讲：

1. 从多个 broker / exchange / offline 位置收集持仓
2. 统一成一个 central repository
3. 给这些持仓补充价格、yield、target 等外部数据
4. 按资产类型分别计算价值、收益和表现
5. 导出到 Google Sheets / spreadsheet 里形成持续可用的监控看板

你可以把这一章理解成：

“个人资产监控系统最小可用架构”

## 核心概念讲解

### 1. 什么叫 asset monitor

很多人会把 monitor 想成：

- 一个列了持仓的 Excel

但作者这里要做的其实更像：

- 一个持续更新的资产控制面板

它要回答的不只是“我持有什么”，还包括：

- 总市值是多少
- 被动收入是多少
- 哪些资产表现最好 / 最差
- 距离财务目标还有多远

所以它不是被动记录，而是：

- 一个让你持续保持 control 和 visibility 的系统

### 2. 这章最重要的系统问题：数据从哪来，而且怎么合并

作者一开始就点出一个现实：

- 你的资产不会都躺在同一个地方

你可能同时有：

- 股票在券商 A
- ETF 在券商 B
- bond 信息一部分手动维护
- crypto 在交易所
- 还有一些完全没有数字接口的 offline asset

这时候真正的难点不是：

- 会不会算涨跌幅

而是：

- 怎么把这些异构来源先统一进一套结构里

这其实已经是非常标准的数据工程问题。

### 3. 一个重要例子：offline assets 为什么也要进系统

作者在 `6.1 Architecture` 里给了一个很实用的例子：

- 有些资产没有数字足迹，比如 real estate

这意味着：

- 不是所有资产都能靠 API 自动拉

他的解决办法不是“那就不管它”，而是：

- 单独建一个 `offline_asset` 表
- 把这些资产手动录进去

这个例子特别重要，因为它说明 monitor 的原则是：

- 先追求全局覆盖
- 再追求自动化

换句话说：

- 半自动但全面
- 往往比全自动但缺一大块资产更有意义

### 4. 一个重要例子：为什么要先定义统一 schema

作者没有一上来就围着某家 broker 写脚本，而是先定义目标数据结构。

这一步很程序员。

比如他要统一管理这些字段：

- ticker
- 持有数量
- 平均买入价
- exchange
- broker

这样做的意义是：

- 不同来源随便乱来没关系
- 只要最后都能落到统一结构
- 后面的 enrichment / processing / export 才能稳定工作

这个例子非常值得你记住，因为它几乎适用于所有个人数据系统：

- 先定义内部标准
- 再写接入层适配外部世界

### 5. 一个重要例子：ticker mismatch 为什么会让系统出错

第六章里有个特别真实的细节：

- broker 给你的 ticker
- 不一定和 Yahoo Finance / Google Finance 一样

作者举的典型例子是：

- `BRK.B`
- 在 Yahoo Finance 里可能变成 `BRK-B`

如果你没处理这个映射，系统就会出现：

- 有持仓
- 但补不到价格或财务数据

所以作者引入了：

- `asset_lookup`
- ticker mapping

这个例子说明一件事：

- 真实系统的问题，很多都出在标识符不一致，而不是算法不够高级

### 6. 一个重要例子：为什么要统一货币

作者还提醒你：

- 你可能同时持有美元资产、欧元资产、其他货币资产

如果不先换成同一货币口径，你看到的总市值、收益、表现就会很混乱。

所以 monitor 里一个非常关键的中间层动作就是：

- currency conversion

这一步的意义不是复杂，而是必要。

### 7. 一个重要例子：同一个框架，为什么 assets 还要分开处理

这章最漂亮的地方之一是：

- 作者把 assets 放进一个 monitor
- 但没有假装它们完全一样

#### 股票（stocks）

股票适合补：

- `currentPrice`
- `targetMeanPrice`
- `dividendRate`

然后计算：

- 当前总值
- 历史收益
- 预期收益
- yield

#### ETF

ETF 可以部分复用股票逻辑，但作者特别提醒：

- 它不是单一公司
- 很多单股指标无法直接套过来

所以在 ETF worksheet 里，有些列会缺失，这是合理的，不是系统失败。

#### bond

债券又不一样。

作者提醒：

- 债券更像通过 `ISIN` 识别
- 处理逻辑更偏向 par value 和 yield
- 不太像股票那样天天靠 target price 跑

#### crypto

crypto 更特殊：

- 持仓可能一部分在 Binance
- 一部分在 ledger
- 价格还不能完全依赖 Google Finance

所以又要接不同 price provider。

这整个例子想教你的不是“资产种类好多”，而是：

- monitor 的框架可以统一
- 但业务逻辑一定要因资产而异

### 8. 为什么作者还在用 Google Sheets

很多程序员看到这里会本能地想：

- 为什么不直接做个 Web app？

但作者这里的思路其实很现实：

- spreadsheet 很适合做展示层
- 它天然支持筛选、汇总、快速查看、手工修正
- 对个人系统来说，足够轻，也足够灵活

所以这章不是在告诉你：

- Google Sheets 是终极答案

而是在告诉你：

- 它是一个非常实用的 first usable interface

### 9. 这一章为什么这么重要

因为它第一次让你看到：

- 投资研究不只是“某次分析”
- 还可以落成“长期维护的系统”

这就是程序员在投资里的 `unfair advantage` 真正开始变得具体的地方。

## 本章最值得抓住的 4 个判断

### 判断 1：monitor 的目标是 control，不是炫技

它是为了帮助你持续管理持仓，而不是展示你会写多少代码。

### 判断 2：多源整合比单源分析更难，也更关键

真正的实务问题，通常出在数据源分散、格式不统一、标识符不一致。

### 判断 3：统一结构是系统生命线

没有统一 schema，后面所有 enrichment、processing、export 都会变得脆弱。

### 判断 4：统一框架不等于统一逻辑

不同资产一定要按不同业务逻辑处理，否则 monitor 只会“看起来统一”，实际却误导判断。

## 第一遍不用深究的内容

为了防止第一遍就陷进实现细节里，你现在可以主动放过这些东西：

- 每家 broker 的 API 参数细节
- SQLite 的全部 SQL 细节
- Google Sheets 权限配置的每个步骤
- 每段 helper function 的具体实现
- 所有 worksheet 的列级别公式

第一遍你真正要抓的是：

- monitor 想解决什么问题
- 为什么要统一 schema
- enrichment 为什么必不可少
- 不同资产为什么必须分开处理
- 为什么这章是“个人研究系统”的雏形
